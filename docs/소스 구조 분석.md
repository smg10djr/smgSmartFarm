# 소스 구조 분석

작성일: 2026-10-03 · 기준 커밋: `b077bb4` (PR #4 머지 직후)

상추 DWC 수경재배 스마트팜 학습 프로젝트의 소스를 읽고 정리한 문서입니다. 파일 안의 코드를 직접 읽은 내용만 적었고, 실행해 보지 않은 동작은 "추정"으로 표시했습니다.

## 1. 전체 흐름

```text
ESP32 ──MQTT──> Mosquitto ──> bin/mqtt_subscriber ──> (ActiveJob) ──> 서비스 ──> PostgreSQL
                                                                            │
                                         브라우저 <── Turbo Streams <── DashboardBroadcaster
```

| 단계 | 담당 | 하는 일 |
|---|---|---|
| 1. 측정·발행 | `firmware/src/main.cpp` | DS18B20 수온을 5초마다 측정, 1분 평균을 JSON으로 발행 |
| 2. 중계 | `infra/` Mosquitto | MQTT 브로커 (개발용, 익명 허용) |
| 3. 수신 | `server/lib/smart_farm/mqtt_subscriber.rb` | 토픽을 구독하고 job만 큐에 넣음 |
| 4. 저장 | `IngestSensorReadingJob` → `SensorReadingIngestor` | 검증 후 DB 저장, 중복 처리 |
| 5. 알림 | `WaterTemperatureAlert`, `DeviceStatusUpdater` | 수온 이상·오프라인 알림 열고 닫기 |
| 6. 화면 | `DashboardController`, `DashboardBroadcaster` | 대시보드 표시와 실시간 갱신 |
| 7. 수동 입력 | `ManualMeasurementsController` | 센서가 없는 pH·EC를 사람이 입력 |

## 2. 디렉터리 구조

```text
smgSmartFarm/
├─ CLAUDE.md, README.md        프로젝트 안내, Claude Code 작업 지침
├─ .env.example                DB·MQTT 포트와 비밀번호 샘플 (.env는 Git 제외)
├─ docs/                       계획·테스트 가이드·PRD·이 문서
├─ infra/                      개발용 Docker Compose (PostgreSQL 17, Mosquitto 2)
├─ firmware/                   ESP32 펌웨어 (PlatformIO, Arduino 프레임워크)
└─ server/                     Rails 8 앱 (모든 bin/rails 명령은 여기서 실행)
   ├─ app/
   │  ├─ controllers/          dashboard, manual_measurements
   │  ├─ models/               device, sensor_reading, alert_event, manual_measurement
   │  ├─ services/             ingestor, alert, status updater, broadcaster
   │  ├─ jobs/                 ingest_sensor_reading, update_device_status
   │  ├─ helpers/              dashboard_helper (SVG 그래프 좌표)
   │  └─ views/dashboard/      show + 부분 템플릿 4개
   ├─ lib/smart_farm/          mqtt_subscriber (Rails 밖에서 도는 구독 루프)
   ├─ bin/                     mqtt_subscriber, fake_sensor + Rails 기본 스크립트
   ├─ config/                  routes, database, cable, locales(ko) 등
   ├─ db/                      migrate 5개, schema.rb
   └─ test/                    controllers, jobs, lib, models, helpers, services
```

`app/javascript/`, `app/views/pwa/`, `app/mailers/`, `config/credentials.yml.enc` 등은 Rails 생성 기본 파일이고 프로젝트 고유 로직은 없습니다.

## 3. 서버 (`server/`)

### 3.1 데이터 모델과 DB (`app/models/`, `db/schema.rb`)

| 테이블 / 모델 | 주요 컬럼 | 핵심 규칙 |
|---|---|---|
| `devices` / `Device` | `device_id`(유일), `last_seen_at`, `mqtt_state` | `online?` = `mqtt_state != "offline"` 이고 `last_seen_at`이 5분 이내 |
| `sensor_readings` / `SensorReading` | 기온·습도·수온·조도·`water_low`, `sequence`, `raw`(jsonb) | `(device_id, measured_at)` 유일 인덱스로 중복 방지. 수온 -10~60, 기온 -40~85, 습도 0~100, 조도 0~200000 검증 |
| `alert_events` / `AlertEvent` | `kind`, `message`, `triggered_at`, `resolved_at` | 부분 유일 인덱스: `resolved_at IS NULL`인 같은 `(device_id, kind)`는 1개만. `open`, `recent`(최근 20건) 스코프 |
| `manual_measurements` / `ManualMeasurement` | `ph`, `ec_ms_cm`, `note`, `measured_at` | pH 0~14, EC 0~10, 둘 중 하나는 필수. 오류 문구는 한국어 |

`Device`는 세 테이블을 `has_many ... dependent: :destroy`로 가지고, `latest_reading`, `latest_manual_measurement`를 제공합니다.

### 3.2 수신 (`lib/smart_farm/mqtt_subscriber.rb`, `bin/mqtt_subscriber`)

- `smartfarm/+/telemetry`, `smartfarm/+/status`를 QoS 1로 구독합니다.
- `dispatch(topic, message)`는 토픽 마지막 단계로 분기해서 job을 `perform_later`로 큐에 넣기만 합니다. telemetry는 `IngestSensorReadingJob`, status는 `UpdateDeviceStatusJob`, 그 외 토픽은 경고 로그 후 무시합니다.
- `run`은 연결이 끊기면(`MQTT::Exception`, `SystemCallError`, `SocketError`, `IOError`) 5초 후 재연결합니다.
- 접속 정보는 `MQTT_HOST`, `MQTT_PORT`, `MQTT_USERNAME`, `MQTT_PASSWORD` 환경변수에서 읽습니다.
- `bin/mqtt_subscriber`는 `$stdout.sync = true`와 stdout 로거를 붙여 로그를 터미널에도 보여 주고, INT/TERM 신호에서 정지합니다.

### 3.3 Job (`app/jobs/`) — 얇게 유지

| 파일 | 내용 |
|---|---|
| `ingest_sensor_reading_job.rb` | `SensorReadingIngestor` 호출 → 저장되면 `WaterTemperatureAlert` → `DashboardBroadcaster` 순서로 실행. 결과에 따라 `stored`/`duplicate`/`rejected` 로그를 남김 |
| `update_device_status_job.rb` | `DeviceStatusUpdater` 호출 후 장치가 있으면 `DashboardBroadcaster` 실행 |

### 3.4 서비스 (`app/services/`) — 로직의 중심, `Klass.call(...)` 형태

| 파일 | 역할 | 세부 |
|---|---|---|
| `sensor_reading_ingestor.rb` | telemetry JSON 검증·저장 | `schemaVersion == 1`, `deviceId`, ISO 8601 `measuredAt` 확인. `Device`는 `find_or_create_by!`. 값 범위 위반은 `:rejected`, `RecordNotUnique`는 `:duplicate`. 결과는 `Result(status, reading, error)` 구조체. 저장 후 `last_seen_at`을 `measured_at`과 기존 값 중 큰 쪽으로 갱신 |
| `water_temperature_alert.rb` | 수온 알림 | 24.0℃ 이상이면 `high_water_temp`, 15.0℃ 이하이면 `low_water_temp` 알림을 엶. 해제는 0.5℃ 여유(24 미만으로 0.5 더 내려가야, 15 초과로 0.5 더 올라가야). 같은 종류의 열린 알림이 있으면 새로 만들지 않음 |
| `device_status_updater.rb` | status 토픽 처리 | `online`/`offline`만 허용. `mqtt_state` 갱신, offline이면 `device_offline` 알림 열고 online이면 닫음 |
| `dashboard_broadcaster.rb` | 화면 실시간 갱신 | `dashboard` 스트림으로 `devices`, `manual-section`, `alerts` 세 컨테이너를 통째로 교체. 장치 카드를 개별 교체하지 않고 컨테이너를 바꾸기 때문에 첫 장치도 새로고침 없이 나타남 |

### 3.5 컨트롤러·뷰·헬퍼

| 파일 | 내용 |
|---|---|
| `controllers/dashboard_controller.rb` | `show`: 장치 목록(`device_id` 순)과 최근 알림을 인스턴스 변수에 담음. 루트(`/`) 경로 |
| `controllers/manual_measurements_controller.rb` | `create`: 장치를 찾아 `ph`, `ec_ms_cm`, `note`를 저장. 성공하면 브로드캐스트 후 notice로, 실패하면 오류 문구를 alert로 루트로 리다이렉트 |
| `views/dashboard/show.html.erb` | `turbo_stream_from "dashboard"`로 구독하고 devices, manual_form, alerts 부분 템플릿을 배치 |
| `_devices.html.erb` | `#devices` 컨테이너. 비어 있으면 안내 문구, 아니면 장치별 `_device` 렌더 |
| `_device.html.erb` | 장치 카드: 온라인/오프라인, 최근 수동 측정, 수온·기온·습도·조도·수위, 마지막 수신, 24시간 수온 SVG 그래프 |
| `_manual_form.html.erb` | `#manual-section` 컨테이너. 장치가 있을 때만 pH·EC 입력 폼 표시 |
| `_alerts.html.erb` | `#alerts` 목록. 진행 중/해제됨 구분, 비어 있으면 "알림이 없습니다." |
| `helpers/dashboard_helper.rb` | `water_temp_points(device, now:)`: 최근 24시간 수온을 600×120 SVG polyline 좌표 문자열로 변환. 데이터가 2개 미만이면 `nil` |

### 3.6 설정·실행 스크립트

| 파일 | 내용 |
|---|---|
| `config/routes.rb` | `root "dashboard#show"`, `resources :manual_measurements, only: :create`, 헬스체크 `/up` |
| `config/database.yml` | `POSTGRES_PORT`, `DATABASE_HOST` 환경변수를 읽음 (개발·테스트) |
| `config/cable.yml` | development는 postgresql 어댑터(구독자 프로세스와 웹 프로세스가 NOTIFY로 통신), production은 solid_cable |
| `config/locales/ko.yml`, `config/application.rb` | 기본 로케일 `ko`, 시간대 Seoul, 검증 메시지·속성명 한국어화 |
| `bin/fake_sensor [deviceId]` | 하드웨어 없이 telemetry 1건을 발행 (수온 19.3℃ 고정) |
| `bin/ci`, `config/ci.rb` | rubocop, bundler-audit, importmap audit, brakeman, 테스트, seeds를 한 번에 실행 |

Solid Queue 어댑터는 production에서만 설정됩니다. development에서는 Rails 기본 async 어댑터가 쓰이므로 job이 `bin/mqtt_subscriber` 프로세스 안에서 실행됩니다.

## 4. 펌웨어 (`firmware/`)

| 파일 | 내용 |
|---|---|
| `platformio.ini` | `esp32dev`(실제 DS18B20)와 `esp32dev_fake`(`-DFAKE_SENSOR=1`, 센서 없이 가짜 수온) 두 환경. 라이브러리: PubSubClient, ArduinoJson 7, OneWire, DallasTemperature |
| `src/main.cpp` | Wi-Fi·MQTT 자동 재접속, NTP 시각 동기화, 5초 측정 → 60초 평균 발행. 센서 값이 -10~60℃ 밖이면 버림. `status` 토픽은 retained + Last Will(`offline`)로 연결 상태를 알림. 시계가 안 맞았거나 MQTT가 끊긴 상태의 평균은 발행하지 않음 |
| `src/secrets.h.example` | Wi-Fi, MQTT 호스트·포트·계정, `DEVICE_ID` 샘플. 실제 `secrets.h`는 Git 제외 |

발행 JSON 예: `{"schemaVersion":1,"deviceId":"balcony-01","sequence":3,"measuredAt":"...Z","waterTemperatureC":19.25}`. 서버의 `SensorReadingIngestor`가 이 형식을 검증하므로 스키마를 바꾸면 `schemaVersion`과 펌웨어를 함께 수정해야 합니다.

## 5. 인프라 (`infra/`)

- `docker-compose.yml`: PostgreSQL 17(`127.0.0.1:${POSTGRES_PORT:-5432}`)과 Mosquitto 2(`${MQTT_PORT:-1883}`). 데이터는 named volume에 보관.
- `mosquitto/mosquitto.conf`: `allow_anonymous true`의 개발 전용 설정. 실제 장치를 붙이기 전에 인증과 ACL로 바꾸라는 주석이 있음 (PRD의 P2-3).

## 7. 코드를 읽고 알게 된 점

- 장치 온라인 판정이 `measured_at` 기준이라, 펌웨어 시계가 미래로 틀어지면 `last_seen_at`도 미래가 되어 5분이 지나도 온라인으로 보일 수 있습니다 (추정, 실행으로 확인하지 않음).
- `UpdateDeviceStatusJob`은 `last_seen_at`을 갱신하지 않습니다. status 메시지만으로는 5분 판정이 연장되지 않습니다.
- 화면의 "오프라인" 표시는 브로드캐스트나 새로고침 시점에 계산되므로, 수신이 끊겨도 아무 이벤트가 없으면 5분이 지나도 화면은 바뀌지 않습니다 (코드상 이를 갱신하는 주기 작업이 없음).
- 구독자는 `perform_later`로 job을 넘기는데 development는 async 어댑터라 job이 구독자 프로세스에서 실행됩니다. production은 `bin/jobs` 또는 `SOLID_QUEUE_IN_PUMA=1`로 워커가 필요합니다.
- 보류 범위(`docs/plan.md`): 220V 직접 제어, 자동 pH·EC 주입.
